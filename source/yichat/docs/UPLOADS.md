# 附件上传（0.3.6）

App WebView 和浏览器共用 `media.ts` 与 `upload-transfer.ts`。旧 XHR 发送进度仅代表浏览器发送缓冲，不能证明服务器已保存文件。0.3.6 改为服务器确认的小块传输；不调整 500000 B/s 的共享上行限制。

## 协议

所有请求都沿用主站会话、同源检查和每秒请求限制。每个状态读取、追加及完成请求重新检查会话成员资格和发送权限。

1. `POST /api/uploads`：JSON `{room,bytes,key}`，key 为此文件草稿的随机请求标识。同一用户重复相同 key 返回同一任务；不同房间或长度返回 409。新任务预留整文件日额度及上传名额。
2. `PUT /api/uploads/{id}`：`application/octet-stream`，`X-Upload-Offset` 为起始位置；每块最多 131072 字节。串行写入 `.part`、flush/fsync 后才提交 SQLite offset 并返回确认。崩溃遗留的未提交尾部先截断，重复分块必须字节相同。
3. `GET /api/uploads/{id}`：返回 state、offset、bytes、chunk_bytes。网络错误或丢失回执后先查询，跳过已确认分块。任务 ID 不是授权凭证，其他用户返回 404。
4. `POST /api/uploads/{id}/complete`：收齐后冻结字节及完成时间，重新计算 SHA-256，原子改名并 fsync 目录；先写 PostgreSQL 附件回执，再写原 files/file_hashes 并释放上传名额。只有 complete 返回 mxc URL。任何阶段重复完成均使用相同文件 ID 和回执，归档故障保持 finalizing 并允许重试。
5. `DELETE /api/uploads/{id}`：仅取消上传中草稿；不删除完成中或已完成附件。15 分钟无进展的草稿由维护任务清理，完成中的任务重试确认并保留文件证据。

客户端每次只提交 Blob 切片，不调用整文件 arrayBuffer。每个请求 30 秒超时，暂时错误最多 4 次尝试并退避；永久权限错误直接停止。手动重试保留当前页面内任务 ID。410 过期后清除该任务，下一次重试创建新的随机标识。刷新或重新选择文件不会从本地持久化恢复旧任务。

## 兼容和约束

- 单文件最大 100000000 字节，上传名额 3，原日额度和共享虚拟时钟不变。重传已确认分块的字节仍计入日额度。
- 新任务初始预留整文件额度，失败不退额度；重试同一任务不会重复预留整文件。
- 旧 `POST /api/files/{room}` 保留给旧客户端，下载、房间权限、消息发送确认和附件 SHA-256 验证不变。
- 上传 journal 只保存任务元数据，不保存消息正文。未完成草稿不出现在聊天，不触发付款、赠卡或消息发送。
- 不修改 epoch，不清空聊天，不修改钱包或资产。日志不写文件内容、授权头或私钥。

## 验证

专用隔离数据库测试覆盖完整下载字节与哈希、重复 key/分块、未提交磁盘尾部、归档确认失败、取消及越权。真实 uvicorn TCP 测试分段发送 64 KB、256 KB、700 KB 数据。Chromium 使用超过 200 KB 的有效 PNG，提交第一块后主动丢弃响应、完成后再次丢弃响应，验证查询恢复、正确块数、接收端图片和完整字节一致。

真机回归：App 覆盖升级后打开一次；手机 Chrome 刷新页面。在两端分别发送几百 KB 图片和文件，观察确认进度与接收端下载；上传中切换 Wi-Fi/移动网络、短暂断网再恢复，长时间断网失败后点击重试。刷新页面会新建任务。原手机最初的具体网络断连原因尚未在源站复现，故障注入结果不代表已定位运营商/CDN 原因。
